Approval and lens flow

How the Chamber Tauri gRPC POC splits a turn between a sidecar that acts and a host that consents.

The sidecar owns its tools. When the agent calls lens_upsert, the tool runs inside the sidecar, validates the lens, and writes it into the mind directory. What travels backwards is not the work, it is the permission to do it.

Before a tool with side effects runs, the sidecar emits an ApprovalRequest up the same stream it is streaming text down, and blocks until an ApprovalDecision comes back. That single gate is the security model. Everything else is framework portability.

Two boundaries, not one

The sidecar boundary is a framework boundary. Framework types stop at the protobuf contract so PydanticAI can be swapped for something else without rewriting Chamber. It is not a privilege boundary, and nothing in the design pretends otherwise. The sidecar has a filesystem, and it uses it.

The privilege boundary is the approval gate. Security is policy, expressed two ways: the user approves an action before it happens, and a mind is only given the tools it should have. A mind whose only tool is a sandbox runner cannot touch anything else, no matter what the model decides.

The four layers

The webview runs React and knows nothing about agents. It receives chat-event and lens-event, both in Chamber's own shapes, and renders chat text plus lenses in sandboxed iframes. No gRPC, no model, no framework types.

The Rust core is a single process with three jobs: the sidecar process lifecycle, the consent channel, and the renderer. It spawns sidecars, mints the auth token, holds the tonic client, answers approval requests, and fans events out to the webview.

The Chamber Agent Protocol is the seam. Six event types, two host messages, all in Chamber's vocabulary. No framework concept survives the crossing.

Sidecars run one per mind, each in its own OS process, each owning an agent loop, a model connection, its tools, and its mind directory. Isolation is per mind: crash, memory, credentials, model choice, framework version.

The shape of a turn

One gRPC call, Interact, holds two independent streams open for the whole turn. Text flows down. Approval decisions flow up. Neither closes until the turn ends.

Inside the sidecar there is a trick that makes this work. The servicer function cannot both await the agent and await incoming decisions, so it does neither. It becomes a pump over an asyncio.Queue, and two background tasks feed it.

Why each piece is there

Approval is native, not bolted on

ApprovalRequiredToolset wraps the tool and raises ApprovalRequired before the body runs. The HandleDeferredToolCalls capability intercepts that, calls an async handler, and resolves it inline in the same run. There is no second run, no output type change, and no message history to replay. The suspension happens where the tool call happens.

The tool call ID comes from the framework

Correlation uses PydanticAI's own tool_call_id. The sidecar mints nothing, so there is no second identifier space to keep in sync, and the ID in an ApprovalRequest is the same ID that appears in the model's transcript.

Denial is not an error

A denial resolves as ToolDenied, which returns a message the model reads and adapts to. The run keeps going. ModelRetry is reserved for arguments the model can fix and consumes the retry budget. ToolFailed reports a write that definitively failed. Three outcomes, three meanings, none of which kill the turn.

LensChanged carries the whole lens

An id-only event would force Rust to read from disk, and there are real races there. The manifest and the HTML are two separate writes, the framework can run sibling tool calls concurrently, and Rust already allows concurrent sessions against one runtime. Rust could load a half-replaced lens or mix one revision's manifest with another's HTML. Carrying the snapshot removes the race and the second read path, and costs nothing: the same HTML already crossed the wire in the ApprovalRequest.

Rust still validates what it renders

The sidecar validates before writing, so the model gets a usable reason when the lens is malformed. Rust revalidates the incoming snapshot before handing it to the webview. That second check is not distrust of the mind, it is the renderer refusing to display something it cannot display safely.

Dropping the stream unblocks everything

Rust drops ChatStream, the mpsc sender dies, the request iterator ends, the reader closes the bridge, and any approval waiting on a future raises instead of hanging. The bridge stays closed, so an approval requested afterwards fails immediately rather than waiting on nobody. Cancellation propagates through the tool boundary without a cancel message existing in the protocol.

What this POC does not do

Rust auto-approves every request. There is no approval UI, no pending state, no timeout, and no way for the user to say no. The plumbing is real and the decision is not. Calling the current behaviour consent would be a lie.

Also absent on purpose: multi-turn prompts on the open stream, message history, session resume, health checks and restart policy, and a sandbox for tools that need one.
